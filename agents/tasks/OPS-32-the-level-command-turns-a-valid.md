## Why

Levelling is the step that turns what a customer said into what we build: runtime, identity, autonomy, data controls, connectors, memory and plan fit per task, each traceable to a compendium page. The first adversarial review found three traps this must respect (Agent SDK cover under ZDR and HIPAA is unconfirmed; autonomy is enforced per connector tool, not per task; a Team plan with no device management loses hooks and logs). The persona card is card.json, not the persona voice file in starter-kit/templates/persona and not a task card.

It first runs validate; when validation has errors it levels nothing. It builds a flat set of named facts per task from the card, the profile and the industry pack (for example task.trigger, task.data_class, task.output.audience, task.reversible, task.touches_money, task.cost_of_mistake.level, task.reads_untrusted_input, task.in_pilot, role.works_in, role.device, memory.personal_memory_wanted, plan.tier, identity.scim, devices.mdm, compliance.retention, compliance.phi, compliance.baa, governance.action_log_required, runtime_preferences.self_hosting_required, and the decisions already made such as runtime). - levelled.json has this shape, written with a fixed key order, two-space indent, UTF-8, a trailing newline, and no date or machine-specific value, so the same inputs always give the same bytes: {levelled_version: 1, customer, persona, source: {card_sha256, profile_sha256, rules_version, pack}, persona_plan: {plugin_name (the card's role.plugin_name when it is given, otherwise 'twin-<persona id>'; a given name that does not match ^twin-[a-z0-9-]+$ is a blocker with a fix sentence), distribution, settings_baseline, starting_points (the pack's anthropic_starting_points, unchanged, with their cite and unverified)}, tasks: {<task id>: {runtime, identity, autonomy: {start, ceiling}, data_controls: {settings_baseline, web_tools, surfaces, retention}, connectors: [{system, access, identity, how, runbook, permission, cite, unverified}], memory, plan_fit}}, tools: [...], blockers: [...], warnings: [...], complete}. Every decision is {value, rule, cite, reason, unverified, basis, overridden}: rule is the id of the rule that decided it, reason is one plain sentence a consultant can read to a customer, overridden is null or {rule_result, reason, approved_by} (rule_result is the name the expectations file's override variant uses). A decision no rule can make because the card field it needs is open has value null, rule null and a reason naming the open field path, plus a warning. A rule may also decide 'undecided': its then is null, the decision's value is null, the rule id is kept, the reason says what the cited page lacks, and the task gets the decision-undecided warning (the expectations file expects this for the autonomy ceiling of the two PE tasks with a high cost of a mistake; do not fill those in). Blockers and warnings are {code, about, cite, unverified, message, fix}: message says what is wrong in plain words and fix says what the consultant does next.
- Overrides: an entry in the card's overrides[] replaces the rule's value for that task and decision; the decision keeps the rule id and records overridden {rule_result, reason, approved_by}. Blockers, warnings and plan_fit are worked out after overrides are applied, so an override cannot hide a blocker. plan_fit and connectors cannot be overridden: an override that names one of them, or a task or decision that does not exist, is a blocker with a fix sentence. (If expectations.json's override variant shows a different treatment, follow the file.)
- Tools and per-tool permission (compendium 06, 'How a level is enforced'): a tool is one system plus one kind of use, 'read' for inputs or the write action (create, update, delete, send) for writes. tools[] lists each tool once: {system, use, tasks (the task ids that use it), permission (always-allow, needs-approval or blocked, the strictest any of its tasks needs at its starting autonomy level), wanted (per task, the permission that task alone would take), cite, unverified}. When two tasks want different permissions for the same tool, the strictest wins for both and one warning per tool names the tasks and says the two ways out the page gives (split the tools, or run both at the stricter level). The connector entry on each task shows the permission its tools ended up with.
