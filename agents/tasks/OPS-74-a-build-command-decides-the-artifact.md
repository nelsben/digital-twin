## Why

The persona-card workflow stops at a plan; Ben wants it to cut the skill, plugin or agent each task needs, evaluate it and get it deployed (epic #254). This first card adds the deterministic step after level: it turns each levelled task's runtime into a concrete artifact skeleton and a manifest that the later draft, evaluate, package and deploy steps advance.

## Done when

- Read first: partner-kit/docs/design.md (sections 3, 4.2, 7.2, 7.3, 8 and 'What the generator does not produce'), the epic body (gh issue view 254 --repo nelsben/digital-twin), starter-kit/templates/skill/your-skill-name/** and starter-kit/templates/role-plugin/twin-your-role/**, starter-kit/docs/authoring-skills.md, docs/compendium/03-skills-authoring.md, and the runbooks starter-kit/runbooks/managed-agents.md, claude-tag-routine.md, claude-code-scheduled-task.md and agent-sdk-runner.md. Read only outside scope.
- KINDS AS DATA. New file partner-kit/plugins/twin-consultant/data/build-kinds.json maps every runtime value in design 7.2 to an artifact kind: client-skill -> skill in the role plugin; claude-code-scheduled-task -> plugin skill plus a scheduled-task definition; claude-tag-routine -> skill plus a routine definition; managed-agents and managed-agents-self-hosted -> agent bundle (agent definition, environment definition, the skill); agent-sdk -> runner scaffold plus the skill; none -> listed with reason, nothing built. Each entry names the runbook it follows (repo-relative link with anchor) and the files it scaffolds. A test fails if a runtime value in the design or rules.json has no entry. The build never re-decides a runtime: it reads levelled.json's value and records that decision's rule and cite.
- WHERE A SKILL LIVES. A client-skill or claude-code-scheduled-task skill goes in the role plugin build/plugin/<plugin_name>/skills/<skill-name>/. A skill for a hosted, SDK or Tag-routine task goes in build/skills/<skill-name>/ outside the plugin, so it is not distributed to every member, unless the matching runbook says the runtime loads skills from the org's plugins, in which case it goes in the plugin; the hand-back quotes the runbook line behind the choice for Tag routines.
- SKILL NAME. persona card gains one optional field tasks[].skill_name in data/fields.json (record card, part A2, feeds build, asked by nothing, never counts toward completeness) and an empty string in templates/card.json. validate rejects a value that breaks compendium 03's rule (at most 64 characters; lowercase letters, numbers and hyphens; no 'anthropic' or 'claude') or repeats another task's skill_name, with one line naming the task and ending 'Next: ...'. When absent, build derives a name from the task name (lowercase, hyphens, cut to 64, de-duplicated with -2, -3 in task-id order) and build.json marks it derived.
- SCAFFOLD. New module scripts/twincard/build.py and command `cli.py build <persona-dir> [--all-tasks]`. By default it builds tasks with in_pilot true; --all-tasks adds the rest. It writes under <persona-dir>/build/: the role plugin's .claude-plugin/plugin.json (name = persona_plan.plugin_name, from the role-plugin template's shape) and README; per built task the skill folder from the starter skill template (SKILL.md, evals/evals.json, evals/trigger-evals.json, references/ only if the template has it); and per kind its wrapper: agents/<task-id>/agent.json and environment.json for hosted agents (environment networking set to limited with an empty allowed_hosts list, model and system left as FILL IN, the skill named by reference), routines/<task-id>/routine.md for Tag routines and scheduled/<task-id>/task.md for scheduled tasks (each a fill-in sheet of that runbook's 'Inputs you need'), sdk/<task-id>/README.md for agent-sdk. Templates the build reads are copied into partner-kit/plugins/twin-consultant/templates/build/ (the plugin reads only its own folder, design section 3); a test asserts each copy equals its starter-kit source byte for byte.
- SEEDING. The SKILL.md keeps the template's FILL IN markers wherever a person must decide, and fills only what the records state, each seeded line saying which field it came from: frontmatter name; a draft description built from the task's output and trigger and still marked FILL IN; Purpose from story_want and story_benefit; the Inputs table from the levelled connectors and tools for that task (system, use, permission, data_class); one 'Start from <name>' line per starts_from entry with its cite; the example counts. evals.json follows skill-creator's schema as starter-kit/docs/authoring-skills.md gives it, with one FILL IN case per counted good example and never fewer than three (compendium 03, 'Evaluate first'); trigger-evals.json has should_trigger true entries seeded from the task's trigger and two FILL IN should_trigger false entries. Nothing invented: no prompt, expected output or model is made up.
- MANIFEST. <persona-dir>/build/build.json holds build_version 1, customer, persona, source (levelled.json's hash, as backlog does), and artifacts: one per task (id = task id) with kind, runtime value with its rule and cite, skill_name and whether derived, in_pilot, runbook link, files (repo-relative path and the sha256 the scaffold wrote), and status. No timestamp. Statuses are the vocabulary scaffolded, drafted, evals-passing, packaged, deployed, verified, plus not-built for runtime none. build computes only scaffolded and drafted: drafted when no file of the artifact still contains 'FILL IN'; it never lowers a status above drafted already in build.json (later cards record those).
- NEVER OVERWRITE. A file that is missing is written. A file whose current hash equals the hash build.json recorded may be rewritten. A file a person has changed is left as it is and listed on stderr as kept. A second run on unchanged inputs is byte-identical for every file. build refuses, writing nothing, with exit 1 and a 'Next:' line, when levelled.json is missing or out of date (same test backlog uses) or reports a blocker; exit 2 cases follow design section 3.
- NO SECRETS. No file build writes holds a key, token, password, org id, tenant id or instance URL; credentials appear only as environment-variable names (for example $ANTHROPIC_API_KEY) where a runbook step needs one. A test scans both samples' build folders for the patterns sk-ant-, xox, a 15- or 18-character Salesforce id shape after 'org', and https:// URLs other than the docs and vendor-docs hosts already cited in the runbooks.
- SAMPLES. Run build on both fictional samples: engagements/sample-pe/personas/deal-team-associate and engagements/sample-team-cs/personas/customer-success-manager.
