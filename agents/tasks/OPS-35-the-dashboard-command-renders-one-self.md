## Why

The dashboard is the page a sponsor and a consultant look at together: it must show at a glance what the customer asked for, what we decided and why, what is still open and what is left to build. The first adversarial review found no dashboard, scorecard or status view anywhere in the repo. It is a rendering only: every value comes from card.json, the customer profile, levelled.json or backlog.json. The persona card is card.json, not the persona voice file and not a chassis task card.

## Done when

- Read first, whole: partner-kit/docs/design.md (sections 1 to 5, 7.2, 8 and 9), tests/fixtures/twincard/expectations.json (the dashboard block of each fixture, and the blockers, warnings and unverified flags it refers to), tests/test_twincard_acceptance.py, scripts/twincard/cli.py, validate.py, level.py and backlog.py (read only), and both fixtures' card.json, customer-profile.json, levelled.json and backlog.json. tests/fixtures/twincard/expectations.json is fixed: you may not edit it. Where this card and that file disagree, the file wins; say so in the report.
- scripts/twincard/dashboard.py exists, standard library only, Python 3.9 syntax, no network. render(persona_dir, date) returns the page as a string and never writes; write_dashboard(persona_dir, date) writes <persona-dir>/dashboard.html. It reads card.json, the customer profile, levelled.json and backlog.json from disk and the completeness figures from validate. When levelled.json or backlog.json is missing, or a source hash in either does not match the file it was made from, it renders nothing and reports which file is missing or out of date and the command to run next.
- The page is one self-contained HTML5 file: all CSS inline in one style element, no script element and no JavaScript at all, no external request of any kind (no link or img or font or url() that names http, https or //), no file reference outside the page. Collapsing uses details and summary. Every value that comes from a card, profile, levelled or backlog field is HTML-escaped; a test puts '<script>alert(1)</script>' and a double quote into a card text field and a system name and finds them only escaped. Cites are shown as text (page file name and anchor), not as links, because the page may be published where repo paths do not resolve.
- Layout and theme: a <title> of two to four words (the role name plus 'twin'); colours defined once as CSS custom properties on :root, redefined for dark under @media (prefers-color-scheme: dark) guarded by :root:not([data-theme="light"]) and again under :root[data-theme="dark"]; body has an explicit background and colour; readable at 360px wide with a 16px side gutter and no horizontal page scroll (tables either stack or scroll inside their own container); system font stack; a status is never shown by colour alone (each has a word or a symbol with a text label); headings in order h1, h2, h3; a print style that expands every details element. Keep the design plain and dense: this is a working page, not a marketing page.
- The seven sections appear in the order and with the names in the expectations file (Header, Anatomy grid, Feature list, Blockers and warnings, Backlog, Open questions, Where each answer came from), each as a section element with data-section set to that name and an id that is the name in kebab-case. A short table of contents links to them.
- 1 Header: role name, customer display name, a plain 'Fictional sample' label when the profile's fictional flag is true, plan tier, industry pack, pilot users and headcount, completeness as a percentage with the count of required fields answered, the word Complete or Not complete with the reasons it is not (missing required fields count, open questions that block an in-pilot task, blockers), the role plugin name, distribution and settings baseline, and the generated date. One line gives the three numbers a sponsor asks for first: tasks in the pilot, blockers, and backlog tasks done out of total.
- 2 Anatomy grid: nine panels, A1 to A9 with the names design.md section 5 gives them. Each panel shows the decisions that belong to that part for this persona (for example A4 runtime: the count of tasks per runtime; A5 identity: per identity; A7 guardrails: settings baseline, web tools, autonomy start and ceiling range; A6 memory: on or off per task and whether the role wants it; A3 connectors: each system with read or write and its tool permission; A9: distribution, governance log, plan-fit limits), how many of its card fields are answered out of required, and how many backlog tasks of that part are done out of total. Which decision sits in which panel is a table at the top of dashboard.py, and design.md section 9 lists it.
- 3 Feature list: each feature with its tasks in card order; per task the name, in pilot or later, priority, trigger, data class, runtime, identity, autonomy as 'start to ceiling' ('undecided' for a null), memory, plan fit, connectors with access and permission, the one-sentence reason of each decision inside a details element, an 'Unverified' label on every decision whose unverified flag is true, and an 'Overridden' label with the rule's own result, the reason and who approved it on every overridden decision. Every decision cell carries data-decision="<task id>.<decision>" using the names in the expectations file (autonomy.start, autonomy.ceiling), and data-unverified="true" when it is unverified.
- 4 Blockers and warnings: blockers first, then warnings, grouped by what they are about (the persona, then each task), each with its code, message, fix sentence, cite as text and an 'Unverified' label when its flag is true. Each entry carries data-code="<code>" and data-about="<about>", and data-unverified="true" when unverified. A third list, 'Rests on an unverified fact', names every unverified decision and every unverified code in one place. When there are no blockers the section says so in words.
- 5 Backlog: the epic, then features, stories and tasks as nested details elements, each with its id, status word and, for a feature and the epic, done out of total; a story shows its statement, what gates it and its tasks with owner role; a task shows its how steps and done-when. Retired items are listed last when there are any. 6 Open questions: each with id, question, the tasks it blocks, owner and due date, the ones that block an in-pilot task first. 7 Where each answer came from: counts of fields by provenance status (answered, default, assumed, open) for the card and for the profile, then every field whose status is assumed or open with its path, owner and due date, and the list of interview files the card cites.
- The generated date is the only date on the page and comes from --date YYYY-MM-DD; with no --date it is today's date. A date that is not a real calendar date is a usage error. The same inputs and the same date give the same bytes.
- cli.py gains: dashboard <persona-dir> [--date YYYY-MM-DD]. It writes dashboard.html and prints the path and one line with completeness, blockers, warnings and backlog done out of total. Exit codes: 0 when written and the levelled plan has no blocker; 1 when validation has errors or levelled.json or backlog.json is missing or out of date (nothing written), or when the levelled plan has a blocker (the page is still written, so it can show the blockers); 2 on a usage error. validate, level and backlog keep working exactly as now.
- dashboard.html is committed for both fixtures (engagements/sample-pe/personas/deal-team-associate and engagements/sample-team-cs/personas/customer-success-manager), each produced by the command with --date 2026-11-15, never by hand.
- tests/test_twincard_dashboard.py (standard library, html.parser for reading the page, temp folders for anything it writes) covers: the page parses with every tag closed and no duplicate id; no script element, no on* attribute, no external reference; the escaping case; the seven sections in order; nine anatomy panels; every card task appears in the feature list with all its decisions; a null ceiling shows 'undecided'; an override variant from the expectations file shows the Overridden label with the rule's result and reason; a blocker variant shows the blocker and the header says Not complete; the missing and out-of-date input cases; the date rules; exit codes including 'blocker still writes'; byte-identical output on two runs with the same date; the three theme rules are present in the style element; and the page stays under 600 KB for both fixtures.
- tests/test_twincard_acceptance.py gains, above its closing comment block and without weakening any existing check: for both fixtures, the data-section values of a fresh render equal the expectations file's dashboard.sections in order; every code in dashboard.must_show.codes appears as a data-code; every '<task>.<decision>' in must_show.unverified is a data-decision cell with data-unverified true, and every '<code>:<about>' in it is an entry with that data-code and data-about and data-unverified true; no decision or code is marked unverified that the expectations file does not list; the header shows the completeness percentage and the complete flag the expectations file gives for validate; the committed dashboard.html equals the bytes of a fresh run with --date 2026-11-15.
