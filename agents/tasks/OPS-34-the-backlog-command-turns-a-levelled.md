## Why

The backlog is what the consultant and the customer build from: it must read like a feature epic with stories and tasks, each task saying how to do it with the kit's own templates and runbooks. The first adversarial review found that the hand-written sample backlog has no feature level, tasks without steps and no status. The persona card is card.json, not the persona voice file in starter-kit/templates/persona and not a chassis task card; the generated backlog is per customer and is not this repo's GitHub issues.

Each template is {id, title, part, applies_to, when, how, done_when, owner_role}. id is stable kebab-case and unique. part is one of A1 to A9 as design.md section 5 names them. applies_to is 'task-story' (a story generated from a card task) or the id of one foundation story (S-persona-voice, S-connectors-and-identity, S-guardrails-and-settings, S-distribution, S-governance-log, S-memory-policy, S-pilot-rollout-and-scorecard). when uses the same data-only condition language as rules.json (reuse level.py's evaluator; do not write a second one) over facts of the story: the card task's fields, its levelled decision values, its blocker and warning codes, the kinds and products of the systems it reads and writes, and persona facts (plan.tier, role.device, distribution, settings_baseline). An empty when always applies. how is a list of at least two steps; each step is {text, link}: text is one imperative sentence a consultant or the customer's admin can follow, link is null or a repo-relative path (with an optional #anchor) to the kit template, runbook, compendium page or playbook page the step uses. done_when is a list of at least one checkable sentence. owner_role is one of owner_roles, which you take from the roles in docs/playbook/03-stakeholders.md plus 'consultant' and 'skill-owner'; list them in design.md. - scripts/twincard/backlog.py exists, standard library only, Python 3.9 syntax, data found relative to its own file, no network. build(persona_dir) returns the backlog as a dict and never writes; write_backlog(persona_dir) writes backlog.json and backlog.md into the persona folder. It reads card.json, the customer profile and levelled.json from disk. When levelled.json is missing, or its source.card_sha256 or source.profile_sha256 does not equal the current files, it builds nothing and reports 'levelled.json is missing or out of date. Next: run the level command.'
- backlog.json has this shape, written with a fixed key order, two-space indent, UTF-8, a trailing newline and no date or machine-specific value, so the same inputs give the same bytes: {backlog_version: 1, customer, persona, source: {card_sha256, levelled_sha256, library_version}, epic: {id: 'E', title, features: [{id, title, kind: 'capability' or 'foundation', stories: [...]}]}, retired: [...]}. The epic title is '<role name> twin for <customer display name>'. Feature ids are 'F-<feature id>' in card order, then 'F-twin-foundation' last. A story is {id, title, statement, part, in_pilot, priority, status, fields, acceptance, gated_by, tasks}. Task-story ids are 'S-<task id>'; the statement is 'As a <role name>, I want my twin to <task name, first letter lowered> so that <the task's outcome sentence from the card>'; fields is the playbook 04 story-template table filled from the card and levelled.json (data class, surface, autonomy as 'start to ceiling' with 'undecided' for a null, connectors and identity, wall impact, inputs, output and audience, skill owner, baseline as frequency per week times minutes each times users); acceptance is the card task's examples as eval placeholders plus the fixed 'Plus' line items that apply (no web tools when web_tools is off; every write carries the twin marker when the story writes to a CRM; tool calls reach the governance log when the plan has one). Stories inside a feature are ordered in-pilot first, then by priority, then by card order. The seven foundation stories use the ids in the expectations file, in that order.
- A generated task is {id, template, title, part, how, done_when, owner_role, status}. Its id is '<story id>.<template id>' (not a running number, so adding a template never renumbers existing tasks; update design.md section 8, which now says 'S-<task id>.T3'). A template that applies once per connector, per decision or per code adds the system id, decision name or code to the id and the title. Every story has at least one task. gated_by on a story lists {kind: 'blocker' or 'open-question', id, text}: each levelled blocker about that task or about the persona, and each card open question whose blocks list names the task. A story with a blocker in gated_by is still generated.
- Status: every epic, feature, story and task has status 'todo', 'in-progress' or 'done'. A fresh run gives 'todo'. When backlog.json already exists, an item whose id is still generated keeps its status; an item whose id is no longer generated and whose status was not 'todo' moves to retired[] as {id, title, status}, and the command prints one line per retired item. A status outside the three values in an existing file is a usage error that names the id. A feature's or the epic's status is not stored by hand: it is 'done' when all its children are done, 'todo' when all are todo, otherwise 'in-progress'.
- backlog.md is the readable form of the same data and nothing else: the epic as the title, one section per feature, one sub-section per story with the statement, the fields table, the acceptance list, what gates it, and its tasks as a checklist ('- [ ]' todo, '- [~]' in-progress, '- [x]' done) with owner role, the numbered how steps with their links written relative to the persona folder so they resolve from where the file sits, and done-when. Its first line after the title says it is generated from card.json and levelled.json and is never edited by hand, with the command to regenerate it.

It writes the two files and prints the epic title, then per feature the count of stories and tasks, then one total line. --plan-out also writes the tree_import plan shape {"version":1,"items":[{"type","title","note","children"}]} with types epic, feature, story and task, each note holding the id and, for a task, the how steps and done-when; nothing is filed anywhere. Exit codes: 0 when written and the levelled plan has no blocker; 1 when validation has errors or levelled.json is missing or out of date (nothing written), or when the levelled plan has a blocker (both files are still written); 2 on a usage error. validate and level keep working exactly as now.
