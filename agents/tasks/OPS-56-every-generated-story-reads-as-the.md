## Why

The outputs review (findings 2, 7 and 10 in .delegation/reviews/2026-11-16/outputs/findings.md) found that generated stories do not follow docs/playbook/04-stories.md: the statement is built from the task name and reads as broken English, there is no target line, placeholder acceptance lines look like real evals, the definition of ready and done is not checked, and open questions never become spikes. Ben's target is a backlog a consultant can hand to an engineer as a feature epic with stories and tasks, so each story has to stand as a story.

## Done when

- Read first: docs/playbook/04-stories.md (hierarchy, story template, definition of ready, definition of done), partner-kit/docs/design.md (the card, backlog and task-library sections), /Users/bennelsen/Documents/digital-twin/.delegation/reviews/2026-11-16/outputs/findings.md (findings 2, 7, 10; it judged an older main, so check each point against your base), and backlog.py as it stands after OPS-55 (it already has a delivery field, owner names and an unnamed-roles list: keep them).
- STATEMENT FIELDS. The persona card gains two optional string fields in data/fields.json: `tasks[].story_want` (a verb phrase that completes 'I want my twin to ...', asked by F1) and `tasks[].story_benefit` (a clause that completes 'so that ...', asked by F1 and F3). Both: record card, not required, not a key, part A2, feeds backlog:story. They never change a levelling decision and never count toward completeness. templates/card.json carries them empty. The filling-persona-cards skill (SKILL.md and references/field-rules.md) tells Claude to write them from the interviewee's own words, in the first person of the role, and to leave them empty when the notes do not say why the person wants it; it must not invent a benefit. templates/interview-guide.md gains one follow-up line under F1 that asks what the person would do with the time or what gets better; do not add a new question id.
- STATEMENT. A task story's statement is exactly 'As a <role.name with a lower-case first letter>, I want my twin to <story_want> so that <story_benefit>.' Fallback for an empty story_want: 'produce the <output.what with a lower-case first letter>', or when output.what is also empty 'do the task "<task name>"'. Fallback for an empty story_benefit: when minutes_each is a number, 'I get back the <minutes_each> minutes it takes me each time'; otherwise 'I do not have to do it by hand'. Each task story gains `statement_source`: 'card' when both parts came from the card, else 'drafted'. backlog.md prints after a drafted statement the line '(Statement drafted by the kit: confirm the wording with the interviewee.)'. No statement in any sample or test scenario contains 'twin to <a noun phrase with no verb>': a test asserts every task-story statement's want part begins with a word from the card's story_want or with 'produce' or 'do'. Foundation stories keep their statement.
- TARGET. Each task story gains `target`: {text, set}. When outcome.scorecard_targets has entries, text is 'Target: ' followed by each '<metric>: <value>' joined by '; ', then '. Today: <frequency_per_week> per week, <minutes_each> minutes each, <users> users.' and set is true. When the list is empty, text is 'Target: not set. Agree the scorecard targets with the sponsor before the pilot starts.' and set is false. backlog.md prints the text under the acceptance lines of every task story, and its summary gains one line 'Stories with no target: N' when N is above zero. The generator invents no number.
- ACCEPTANCE. When a task has no counted examples, the three lines that today begin 'Eval 1 of 3: written from a real example ...' are replaced by one line: 'To write: collect at least 3 real examples from <skill owner name, or "the skill owner (not named yet)"> and write one eval case from each.' Real example lines keep their wording. For a task story whose runtime is a client skill, add 'Plus: the skill triggers on the phrases its trigger evals list and stays quiet on the near-misses.' Keep the other Plus lines exactly as OPS-55 left them.
- READY. Each task story gains `ready`: a list of four checks in this order, each {check, met, note}: 'fields' (met when data class, surface, autonomy and identity are all decided: none is undecided or open; note names the undecided ones), 'examples' (met when examples.good plus examples.bad is 3 or more; note gives the count), 'connectors' (met when every system the task reads or writes has a connector decision that is not undecided and no blocker names it; note names the system that fails), 'compliance-sign-off' (present only when the task's data class is highly-sensitive or phi; met only when the story's compliance-sign-off task has status done). backlog.md prints 'Ready to build: yes' or 'Ready to build: no' with one line per unmet check, and the summary prints 'Stories ready to build: N of M'.
- COMPLIANCE SIGN-OFF. data/task-library.json gains template `compliance-sign-off` (owner_role compliance, part A7, applies to task stories whose data class is highly-sensitive or phi): compliance reads the story's fields, the levelled decisions and the data controls, and records the sign-off in the customer's engagement folder; done when the sign-off is recorded with a name and date. Its how link is docs/playbook/04-stories.md#definition-of-ready-before-building unless a more specific existing page covers it. The story's gated_by gains an entry of kind 'sign-off' with id 'compliance' until that task is done.
