## Why

A new consultant must be able to run one command on a persona folder and get the levelled plan, the backlog and the dashboard, and the two fictional examples must prove that the committed results are what the scripts produce. The persona card is card.json (not the persona voice file in starter-kit/templates/persona, and not a task card in agents/tasks); the generated backlog is the per-customer one, not this repo's GitHub issues. The design of record is partner-kit/docs/design.md; a design change is made in that file in this same PR.

## Done when

- Read first, whole: partner-kit/docs/design.md, partner-kit/plugins/twin-consultant/README.md, scripts/twincard/cli.py and the modules it calls (validate.py, level.py, backlog.py, dashboard.py), tests/fixtures/twincard/expectations.json, tests/test_twincard_acceptance.py, and both fixtures' folders under engagements/.
- cli.py gains the command 'all <persona-dir> [--date YYYY-MM-DD]'. It runs validate, level, backlog, dashboard in that order by calling the same functions the single commands call (no second copy of their logic). It stops only when validation fails: then nothing is written and the exit code is 1. A levelling blocker does not stop it: levelled.json, backlog.json, backlog.md and dashboard.html are all written, so the dashboard shows the blocker, and the exit code is 1. The exit code is 0 only when validation passes and there is no blocker; 2 for a usage error or a missing folder. --date is passed to the dashboard step only and defaults to today. It prints one line per step: the step name, 'ok', 'blocked' or 'failed', and the file written; after a failed validate it prints the validator's '<record>:<path>: <message>. Next: <fix>' lines and names the steps it skipped.
- The level command's printed summary gains one line per task, before the blockers and warnings: the task id and its seven decisions (runtime, identity, autonomy as 'start to ceiling' with 'undecided' for a null, settings baseline, memory, plan fit, and the connector systems with read or write). The existing '<kind>: <about> <code>: <message> Next: <fix>' lines and the closing total line stay as they are; --json output and levelled.json do not change. 'all' prints the same per-task lines once. The plugin README's Level section shows the new line. (OPS-32 left this line out; its card asked for it.)
- partner-kit/docs/design.md section 3: the comment on the 'all' line now says what the command does (the four in order; stops only when validation fails; a levelling blocker still writes every file and exits 1). If another sentence of the design says 'all' stops at the first failure, change it to agree. Change nothing else in the design.
- tests/test_twincard_end_to_end.py (standard library only; runs under both 'python3 -m unittest discover -s tests' and 'python3 -m unittest tests.test_twincard_end_to_end'; it calls cli.py as a subprocess with sys.executable, the way a consultant runs it, and writes only inside a tempfile.TemporaryDirectory). For each fixture in expectations.json: copy the customer folder (customer-profile.json and the persona folder with card.json and interviews/) into the temporary folder keeping the layout <customer>/personas/<persona-id>/, without levelled.json, backlog.json, backlog.md and dashboard.html; run 'all <copy> --date 2026-11-15'; assert the exit code is 0 when the fixture's expected blockers list is empty and 1 otherwise; assert each of the four generated files equals the committed file under engagements/ byte for byte, and on a difference show the first differing line of each file.

When the two fresh runs agree with each other but not with the committed file, the committed file is stale: regenerate it by running the single command or 'all --date 2026-11-15' on the folder under engagements/, change nothing in it by hand, and list each regenerated file with the reason in the report.
