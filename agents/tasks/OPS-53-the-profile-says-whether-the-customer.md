## Why

The consultant-walk review (.delegation/reviews/2026-11-16/walk/findings.md, findings 1, 10, 11, 12, 13 and its list (c) "interview content with nowhere to go") showed that a customer with no ZDR cover gets only a warning for highly sensitive work, and that business rules, deadlines and wishes said in an interview have no field and never reach the backlog or the dashboard. Ben's target is a persona card that names every component a deployable agent needs, so what the interviewee said must land somewhere a builder reads.

## Done when

- ZDR COVER FIELD. fields.json gains the profile field `compliance.zdr_cover`: type enum, values `in-place`, `planned`, `none`; required true; no default; asked_by C3; part and feeds follow the neighbouring compliance fields. Meaning, written in the design and the filling skill's customer-profile reference: in-place = a zero-data-retention agreement covers the org or workspace the highly sensitive work will run in today; planned = the customer intends to get it and it is not signed; none = the customer has none and does not plan one.
- DISCOVERY QUESTION. docs/playbook/02-discovery.md question C3 gains one sentence that asks it ('Is zero-data-retention cover in place, planned or not available?'), worded to fit the table; no new question id. The filling skill reads C3 for the field. If the customer's plan cannot have ZDR by compendium 09 or 10, the skill still records the customer's answer, not an inference.
- ZDR RULES. rules.json: `block-highly-sensitive-no-zdr` fires for a highly sensitive task when `capability.zdr` is `no` OR `compliance.zdr_cover` is `none` (blocker code unchanged). `warn-zdr-org-not-confirmed` fires for a highly sensitive task when `compliance.zdr_cover` is `planned` or the field is open (no value), and no longer reads `compliance.retention`. With `in-place` neither fires. If the rule grammar cannot test an open (null) fact in a blocker or warning rule, extend level.py the smallest way that does it and describe it in design 7.3. The rule reasons name the profile field. `retention-highly-sensitive-zdr` is not changed. No cross-check between `compliance.retention` and `compliance.zdr_cover` is added (name it as a follow-up in the hand-back).
- The backlog task that tells the engineer to confirm the ZDR org (task-library template for zdr retention) says, when cover is `planned`, that the agreement must be signed before the task goes live; when `in-place` it stays as it is. If the template cannot vary by a profile fact today, add a second template selected by the warning code instead of changing backlog.py's selection logic.
- TASK CONSTRAINTS. fields.json gains the card field `tasks[].constraints`: a list of strings, required false, provenance tracked like other task fields; each item is one business rule or deadline the task must keep, in the interviewee's words (for example 'Acknowledge within 24 hours of the claim arriving'). asked_by: the interview-guide questions whose prompts collect it (read templates/interview-guide.md and choose; if no prompt asks for rules and deadlines, add one prompt line to the best-fitting existing question, F3 or F4; no new question id).
- WANTED CHANGE. fields.json gains the card field `tasks[].wanted_change`: a string, required false; what the interviewee wishes the task did differently from today (for example 'notice by itself when something is 14 days overdue'). It never changes a levelling decision. asked_by chosen the same way as constraints (add one prompt line to an existing question if none asks).
- WANTED SURFACES. fields.json gains the card field `role.wanted_surfaces`: enum-list with the same values as `role.works_in`, required false; where the role says it would rather work. It never changes a levelling decision; when it names a surface not in `role.works_in` the dashboard shows it beside the planned surfaces as a wish.
